Overview
________________
Google Threat Intelligence Platform
Google Threat Intelligence provides a comprehensive and proactive approach to identifying, analyzing, and mitigating security threats. Leveraging Google’s vast infrastructure, global telemetry, and advanced analytics, it delivers actionable insights to enhance an organization’s security posture. Google Threat Intelligence offers capabilities such as threat detection, analysis of malware and phishing campaigns, real-time threat alerts, and intelligence feeds that integrate seamlessly with security tools like SIEM (Security Information and Event Management) and SOAR (Security Orchestration, Automation, and Response) platforms.
Splunk SOAR Platform
Splunk SOAR is a Security Orchestration, Automation, and Response (SOAR) Platform. It combines security infrastructure orchestration, playbook automation, and case management capabilities to integrate the team, processes, and tools. The majority of the companies use SOAR tools for the below-mentioned objectives.
* To automate repetitive tasks to increase practical team efforts and provide attention to mission-critical decisions. 
* To perform automated investigations and reduce the turnaround time to such critical decision-making situations using extensive playbooks designed on the Splunk SOAR Platform.
* To integrate the existing security infrastructure to ensure the active participation of each part in the security defense workflow.

Integration Use Cases

This section describes the use cases provided as a part of this integration.
Configure Asset
Steps to Configure the Google Threat Intelligence Splunk SOAR’s asset
Follow these steps to create an asset for the Splunk SOAR Platform:
1. Log in to the Google Threat Intelligence Platform.
* From the Left Navbar/Menu click API Key.
* Access your API key.
* To obtain the project id, in the URL when accessing GTI Alerts 
   * for example, in https://proactive.virustotal.com/alerts?...&project=projects%2F**your-project-id**
the Project ID is your-project-id


2. Log in to your Splunk SOAR Platform.
* Navigate to the Home dropdown and select Apps.
* Search Google Threat Intelligence from the search box.
* Click on the CONFIGURE NEW ASSET button.
* Navigate to the Asset Info tab and enter the Asset name and Asset description.
* Navigate to the Asset Settings and paste the API key of your Google Threat Intelligence Platform.
* Add the Project ID of your GTI instance in the Project ID parameter.
* Save the asset.
* Now, test the connectivity of the Splunk SOAR server to the Google Threat Intelligence by clicking the TEST CONNECTIVITY button. 










1. Test Connectivity
   1. Action Goal
Initiate a connection to the Google Threat Intelligence system to validate the asset configuration
   2. Action Parameters
Argument Name
	Type
	Required
(Yes / No)
	Default Value
	Description
	API Key
	String
	Yes
	N/A
	Google Threat Intelligence API Key
	   3. Action Workflow
This action will make a rest call to Google Threat Intelligence to check, if the connection is made successful or not. It uses OAUTH 2.0 authentication for Ingest ATD Alerts On Poll, Get ATD Alerts and Update ATD Alert Status Actions.
   4. Functional use cases
The functional use case of the connectivity action is to validate the provided asset configuration parameters.


Endpoint:
 
GET https://www.virustotal.com/api/v3/me


Authentication for Ingest ATD Alerts On Poll, Get ATD Alerts and Update ATD Alert Status Actions


POST https://idp.prod.identity.proactive.virustotal.com/realms/master/exchange/api-key 


Body parameters:
api_key : API Key of the GTI platform


NOTE: The API call fails with 403 for requests module’s User-Agent. Passing the below headers works when using requests module:
{
"Content-Type": "application/json",
“User-Agent": "SplunkSoar",
                }


   5. Action Output
The action displays the success or failure message based on the API response. For a successful run, it displays ‘Test Connectivity to Google Threat Intelligence Passed’ output message and in case of failure scenarios, it displays the message ‘Test Connectivity to Google Threat Intelligence Failed’ with an appropriate output error response.
For the Authentication for Ingest ATD Alerts On Poll, Get ATD Alerts and Update ATD Alert Status Actions, the access token is stored in the state file.

      3. Action Workflow
  







What does on poll do?
It will ingest data from the external system into the phantom server in the form of containers and artifacts. There are two approaches to polling which are mentioned below. 


1. Poll Now (Manual polling)
It will fetch the data every time as per the corresponding asset configuration parameters. It doesn’t store the last run context of the fetched data.


2. Scheduled/Interval Polling
The ingestion action can be triggered at a regular time interval. It will fetch the data every time as per the corresponding asset configuration parameters based on the stored context from the previous ingestion run. It stores the last run context of the fetched data. It starts fetching data based on the combination of the values of stored context for the previous ingestion run and the corresponding asset configuration parameters.


Stored context
It is the concept of storing the context of the previous ingestion run. This concept will be used only for scheduled/interval polling. It will use the state file to store the last run context. This state file will be created for the created asset for the application on the phantom platform.

      5. Checkpoint and Deduplication Mechanism
Alerts are retrieved using a time-bounded filter for update_time, where the lower bound is the update_time persisted in the state file from the previous execution, and the upper bound is the current time. After processing all fetched alerts, the state file is updated with the current time. In subsequent polling cycles, this stored timestamp serves as the new lower bound for alert retrieval.


For ingestion, each alert corresponds to a single container within Splunk SOAR. An artifact is created under the container with the alert details. If an updated alert is retrieved for future polling cycles, an additional artifact is appended to the same container rather than overwriting the existing one.


Artifact-level deduplication is inherently managed by Splunk SOAR at the container level through a hashing mechanism. Each artifact’s content is hashed, and any change in the underlying data results in a new hash.


At the container level, deduplication is ensured by assigning the source_data_identifier to a unique alert identifier.

Overview

Google Threat Intelligence Platform
Google Threat Intelligence provides a comprehensive and proactive approach to identifying, analyzing, and mitigating security threats. Leveraging Google’s vast infrastructure, global telemetry, and advanced analytics, it delivers actionable insights to enhance an organization’s security posture. Google Threat Intelligence offers capabilities such as threat detection, analysis of malware and phishing campaigns, real-time threat alerts, and intelligence feeds that integrate seamlessly with security tools like SIEM (Security Information and Event Management) and SOAR (Security Orchestration, Automation, and Response) platforms.
Splunk SOAR Platform
Splunk SOAR is a Security Orchestration, Automation, and Response (SOAR) Platform. It combines security infrastructure orchestration, playbook automation, and case management capabilities to integrate the team, processes, and tools. The majority of the companies use SOAR tools for the below-mentioned objectives.
      * To automate repetitive tasks to increase practical team efforts and provide attention to mission-critical decisions. 
      * To perform automated investigations and reduce the turnaround time to such critical decision-making situations using extensive playbooks designed on the Splunk SOAR Platform.
      * To integrate the existing security infrastructure to ensure the active participation of each part in the security defense workflow.

            5. Checkpoint and Deduplication Mechanism
Alerts are retrieved using a time-bounded filter for update_time, where the lower bound is the update_time persisted in the state file from the previous execution, and the upper bound is the current time. After processing all fetched alerts, the state file is updated with the current time. In subsequent polling cycles, this stored timestamp serves as the new lower bound for alert retrieval.


For ingestion, each alert corresponds to a single container within Splunk SOAR. An artifact is created under the container with the alert details. If an updated alert is retrieved for future polling cycles, an additional artifact is appended to the same container rather than overwriting the existing one.


Artifact-level deduplication is inherently managed by Splunk SOAR at the container level through a hashing mechanism. Each artifact’s content is hashed, and any change in the underlying data results in a new hash.


At the container level, deduplication is ensured by assigning the source_data_identifier to a unique alert identifier.

Playbook Development
________________
Close ATD Alert
Develop a playbook to automatically update status of ATD alerts on GTI to Resolved when the corresponding container is closed in Splunk SOAR.
NOTE: It’s not possible to trigger the playbook on any container status change except Closed. If the user changes the status to anything other than Closed, the playbook will not trigger, and the status on the GTI will remain unchanged.
